❯ 安全问题？                                                                    

● 好问题。分析一下：

  不存在额外的安全风险，原因是：

  1. freplace 已经能通过 kfunc 间接写入同样的数据。callback 里调用
  bpf_cache_ext_node_set_metadata 和 bpf_cache_ext_node_add_metadata 已经能修改
  node->metadata，只是多了一层函数调用。直接写入并没有扩大可写范围。
  2. freplace 的定位就是完全替换目标函数。代码注释（verifier.c:19724）明确写着
  "to make freplace equivalent to their targets"。dispatcher 的 struct_ops
  callback 本身就有写权限，freplace 替代了这个函数却没有同等权限，是继承链的 bug
  而不是有意的安全边界。
  3. btf_struct_access 本身有类型白名单。bpf_cache_ext_btf_struct_access
  只允许写 cache_ext_list_node、cache_ext_eviction_ctx、cache_ext_admission_ctx
  、mem_cgroup 这几个特定类型，不是无限制写内核内存。
  4. 加载 freplace 本身就需要 CAP_BPF 权限。能加载 freplace
  的人已经有足够的权限做更危险的事。

  唯一需要注意的是实现方式——要从 tgt_prog 找到它所属的 bpf_struct_ops 实例的
  verifier_ops，而不是简单用 bpf_verifier_ops[type]。要改吗？

  Direct S3FIFO MAIN_ITER_FN：

  if (freq < id)

  这两段代码行为不一样！ 以 MAIN_ITER_FN(0)（id=0）为例：

  ┌──────┬────────────────────────────────┬─────────────────────────────────┐
  │ freq │             Direct             │           Dispatcher            │
  ├──────┼────────────────────────────────┼─────────────────────────────────┤
  │ 0    │ 递减到 -1，-1 < 0 → EVICT      │ 不递减，0 < 0 为 false →        │
  │      │                                │ CONTINUE                        │
  ├──────┼────────────────────────────────┼─────────────────────────────────┤
  │ 1    │ 递减到 0，0 < 0 为 false →     │ 递减到 0，0 < 0 为 false →      │
  │      │ CONTINUE                       │ CONTINUE                        │
  └──────┴────────────────────────────────┴─────────────────────────────────┘

  Dispatcher 的 MAIN_ITER_FN(0) 永远不会驱逐任何页面！ 因为 freq 不可能 <

  修复方法：改成和 Direct 一样的无条件递减。现在验证器已经允许写入了，可以直接用
  __sync_sub_and_fetch。

  时递减"的保守逻辑，导致 MAIN_ITER_FN(0) 永远不驱逐任何页面，白白浪费一整轮
  4096 次遍历。现在改回了和 Direct 一致的 __sync_sub_and_fetch
  无条件递减，可以重新跑 benchmark 验证性能了。
